# 瓦片相机专项教程（滚动地图 / 相机跟随）

> 本篇是第九册 §102「滚动瓦片地图相机」的**深入版**。
> 配套工程：`examples/technique_probe14.yaml`（构建产物 `examples/output/technique_probe14.sb3`）。
> 全部代码已通过 build + 四层校验 + 冒烟测试。

---

## 0. 一句话模型

社区里所有滚动相机（挖矿猫4 的 `CAM.x/CAM.y`、百吨王的 `scroll_x/scroll_y`、
忍者冒险的 `X scroll enabled / S2 Scroll X`、双人跑酷的 `CAMERA X / CAMERA SHIFT DX`）
其实都是同一个式子：

```
屏幕坐标 = 世界坐标 - 相机偏移
```

差别只在**相机偏移怎么来**（跟玩家？跟鼠标？固定？）和**地图怎么存**。

| 作品 | 相机变量 | 特点 |
|---|---|---|
| 挖矿猫4 | `CAM.x` / `CAM.y` | 世界宽 `WORLD_(-BLOCK-) World.width`，多层滚动 |
| 百吨王-登山赛车 | `scroll_x` / `scroll_y` | 背景层按不同倍率滚动（视差） |
| 忍者冒险 | `X scroll enabled` / `S2 Scroll X` | 开关式滚动，某些关卡才开 |
| 双人Apple跑酷 | `CAMERA X` / `CAMERA SHIFT DX` | 相机 + 额外偏移（双人分屏/跟随） |
| 纪念碑谷S | `yx` / `yy` + `层序` | 等距投影 + 多层高度（见 §6） |

## 1. 地图怎么存：三种方案

### 方案 A：扁平列表（**本工程采用**）

一个列表存 `地图宽 × 地图高` 个数字，索引 = `行 × 地图宽 + 列`（**Scratch 列表 1 基，+1**）。

```yaml
lists:
  地图: [1,1,1,1, 1,0,0,1, 0,0,1,0, 1,0,0,1]   # 4×4
```

取第 `(x, y)` 格：

```yaml
- set_variable: { var: 瓦片值, value:
    { item_of_list: { index:
        { add: [ { multiply: [ { var: 世界格Y }, { var: 地图宽 } ] }, { var: 世界格X } ] },
        list: 地图 } } }
```

> ⚠️ Scratch 的 `列表项` / `替换列表项` 都是 **O(n)**：384 格还行，3000 格就会卡。
> 大地图请改用方案 B/C，或把热点区域拆成小列表。

### 方案 B：每行一个列表（列表的列表）

`地图` 是「列表的列表」，`地图[行][列]`。优点：按行访问快、地图好编辑；
缺点：Scratch 里没有「列表套列表」的原生类型，得用「索引→再取一次」两步走。

### 方案 C：克隆格子（**最像编辑器，但最贵**）

每个格子一个克隆体，坐标存世界坐标，渲染时按 `世界 - 相机` 定位。
格子多时克隆体数量爆炸（300 硬上限），只适合小地图/局部区域。

## 2. 相机跟随 + 边界钳制（核心）

```
相机X = 玩家格X - 视野宽/2
相机X = max(0, min(相机X, 地图宽 - 视野宽))     ← 钳制
```

**钳制是必须的**：没有钳制，玩家走到地图边缘时，相机会把窗口推到地图外，
出现大片空白（Scratch 背景是白的，非常刺眼）。

IR 配方（自定义积木 `更新相机`）：

```yaml
procedures:
  - name: 更新相机
    warp: true
    script:
      - set_variable: { var: 相机X, value: { subtract: [ { var: 玩家格X }, 6 ] } }
      - set_variable: { var: 相机Y, value: { subtract: [ { var: 玩家格Y }, 4 ] } }
      - if: { cond: { less_than: [ { var: 相机X }, 0 ] }, do: [
          - set_variable: { var: 相机X, value: 0 } ] }
      - if: { cond: { greater_than: [ { var: 相机X }, 12 ] }, do: [
          - set_variable: { var: 相机X, value: 12 } ] }   # 地图宽24 - 视野宽12
      - if: { cond: { less_than: [ { var: 相机Y }, 0 ] }, do: [
          - set_variable: { var: 相机Y, value: 0 } ] }
      - if: { cond: { greater_than: [ { var: 相机Y }, 7 ] }, do: [
          - set_variable: { var: 相机Y, value: 7 } ] }     # 地图高16 - 视野高9
```

> ⚠️ **自定义积木是「每个角色一份」**：舞台上定义的过程，其它角色**调用不到**。
> 所以要么把过程放在真正要用它的角色上（本工程放在玩家角色上），
> 要么用广播让舞台统一算（见 §5）。

## 3. 只画「窗口内」的格子

渲染时只遍历相机窗口覆盖的 `视野宽 × 视野高` 格，
而不是遍历整张地图 —— 这是滚动地图能跑得动的关键。

```
世界格X = 相机X + 列序
世界格Y = 相机Y + 行序
屏幕X   = (列序 - 视野宽/2) × 瓦片大小
屏幕Y   = (行序 - 视野高/2) × 瓦片大小
```

画格子用画笔画一个方框（四条边）：

```yaml
- goto_xy: { x: { subtract: [ { var: 屏幕X }, 20 ] }, y: { add: [ { var: 屏幕Y }, 20 ] } }
- pen_down: null
- goto_xy: { x: { add: [ { var: 屏幕X }, 20 ] }, y: { add: [ { var: 屏幕Y }, 20 ] } }
- goto_xy: { x: { add: [ { var: 屏幕X }, 20 ] }, y: { subtract: [ { var: 屏幕Y }, 20 ] } }
- goto_xy: { x: { subtract: [ { var: 屏幕X }, 20 ] }, y: { subtract: [ { var: 屏幕Y }, 20 ] } }
- goto_xy: { x: { subtract: [ { var: 屏幕X }, 20 ] }, y: { add: [ { var: 屏幕Y }, 20 ] } }
- pen_up: null
```

## 4. probe14 工程结构

```
舞台（只存数据）
  ├ 地图         24×16 = 384 格的扁平列表
  ├ 地图宽/地图高/视野宽/视野高/瓦片
  └ 相机X/相机Y、玩家格X/玩家格Y、可见瓦片数
玩家（角色，持有「更新相机」过程）
  └ 方向键移动 → 更新相机 → 广播「刷新」→ HUD 说辞
渲染（角色，开了画笔）
  └ 收到「刷新」→ 画相机窗口内的 12×9 格
```

**运行时自检值**（冒烟测试实测）：

| 变量 | 实测 | 含义 |
|---|---|---|
| 相机X / 相机Y | `6` / `4` | 玩家在 (12,8)，相机 = 玩家 - 半视野 ✓ |
| 相机X测试 / 相机Y测试 | `12` / `7` | 玩家贴到 (23,15) → 相机被钳制在 `地图宽-视野宽` / `地图高-视野高` ✓ |
| 相机X测试2 / 相机Y测试2 | `0` / `0` | 玩家走到 (0,0) → 相机被钳制为 0 ✓ |
| 可见瓦片数 | `108` | = 12 × 9，恰好一屏 ✓ |

## 5. 分层视差（多层相机）

背景层用**不同的倍率**滚动，就会自动产生纵深感：

```
远山层：屏幕X = 世界X × 0.3 - 相机X × 0.3
近景层：屏幕X = 世界X × 1.0 - 相机X × 1.0
```

百吨王的做法是多层背景角色各自算 `scroll_x × 倍率`；
也可以直接给每层一个独立的相机变量（`CAM1.x`、`CAM2.x`），
再用 `将 X 坐标增加` 把角色摆到 `世界 - 相机` 的位置上。

**层序（z 顺序）**：Scratch 里用 `go_to_front` / `go_to_back` 控制；
纪念碑谷S 用的 `层序` 变量本质就是一个手动排序表。

## 6. 等距（纪念碑谷S 风格）变体

等距地图不是「方格」，是「菱形格」。两种做法：

**做法 A：世界坐标直接存等距坐标（纪念碑谷S 的 `yx`/`yy`）**

```
格子 (gx, gy) 的屏幕位置：
  sx = (gx - gy) × 半格宽
  sy = (gx + gy) × 半格高
```

于是「走一步」在不同方向上，屏幕位移不一样（右上/左上是两个不同增量）。
这时**相机也要跟着等距变换**：相机存的是「等距坐标」，不是屏幕坐标。

**做法 B：保留正交网格，最后再投影**

碰撞、寻路全在正交网格里算（简单），只有渲染时做等距投影。
适合玩法是方格逻辑、画面想要等距风的作品。

## 7. 五个易踩的坑

### 7.1 相机是「格」还是「像素」？

本工程相机以**格**为单位（整数），所以画面是像素风的，不会糊。
如果要做平滑跟随（像素级），相机改成像素单位：

```
相机Xpx = 玩家像素X - 视野宽像素/2
```

代价：需要做「像素对齐」（把相机取整），否则线条会抖。

### 7.2 相机与玩家的相对位置写死

很多作品把玩家固定在屏幕中心（相机 = 玩家 - 半视野）。
如果玩家在屏幕上的**固定位置**（如左下角），相机公式要改成
`相机 = 玩家 - 固定偏移`。

### 7.3 视野宽是奇数时的取整

`视野宽 = 13` 时 `视野宽/2 = 6.5`，Scratch 的除法会得到小数，
相机变成小数格 → 瓦片对不齐。**要么视野取偶数，要么显式 `mathop floor`。**

### 7.4 边界钳制忘了做

见 §2。地图边缘会出现空白。

### 7.5 列表里存的是「0/1」还是「瓦片 id」

本工程用 0/1（空地/墙）。真实项目往往要存瓦片 id（1=草、2=水、3=桥…），
这时渲染要按 id 选颜色/造型，地图编辑也要按 id 选格子。

## 8. 和 §102 原版的关系

- §102（第九册）给的是**最小可用**模型：一个大背景 + `scroll` 变量平移。
- 本篇给的是**真·瓦片相机**：离散网格地图 + 只画窗口 + 边界钳制 + 分层视差。
- 两者是同一个式子的两种工程量级：大地图用本篇，小场景用 §102 就够。
